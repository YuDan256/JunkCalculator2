## 1. 这个模块做什么

素材是一个**历法转换器**（命令行交互程序：输入公历日期，打印四项）。四件能力：

| # | 能力 | 函数（原文） | 实用价值 |
|---|---|---|---|
| 1 | 公历 → 农历（干支年、生肖、闰月、月/日名） | `LunarCalculator::convert` | **有真实需求**（节日、农历生日、传统日期） |
| 2 | 公历 → 干支纪日（**日**的天干地支） | `DateConverter::getGanzhiDate` | 受众窄（命理、择日、传统历法研究） |
| 3 | 公历 → 罗马历（Kalends/Nones/Ides 倒数式 + A.U.C. 纪年） | `DateConverter::getRomanDate` | **纯趣味，无工程价值**。不假装它有用 |
| 4 | 历法工具（闰年、月天数、JDN） | `DateUtils::*` | 支撑上面三项 |

**它跟"时间戳/时区"没有任何关系。** 见 [`datetime-plan.md`](datetime-plan.md)——那是另一件事。
本模块**不做**：拿"现在"、时间戳 ↔ 年月日、时区、时区转换、通用日期格式化/解析。

## 2. 为什么值得整合（增量价值）

**理由不是"JC2 缺个日历"，而是"从查一个变成算一批"。**

现在它是个独立 exe：交互输入一个日期、打印四行、退出。查 100 个日期就跑 100 次、抄 100 次。

**已实测**：CSV 进 → 逐行变换 → CSV 出这套管线在 JC2 里今天就能跑通
（`D:\Temp\cal_batch.jc2`，用 stand-in 代替将来的 `calendar` 调用）：

```
date,lunarMonth,zodiac

2025-01-29,闰1,2

2024-02-10,闰2,3

1996-09-27,闰0,10
```

进了 JC2 后能和已有的 CSV / 矩阵 / 绘图 / CAS 组合：排 100 年春节对照表、
批量给 CSV 加农历列、统计 1901–2099 哪些年有闰月、把古籍干支纪日批量回推成公历。

**这也是必须返回 Dict 而不是光返回字符串的原因**：字符串只能"看"，Dict 才能"算"。

## 4. 缺陷一：`lunarInfo` 声明 201 项、实际只写了 200 项（越界 UB）

```
std::array<int, 201> lunarInfo = { ... };   // 实际初始值个数 = 200
```

实测：`声明长度 201，实际初始值个数 = 200`。

连锁后果：

1. `lunarInfo[200]`（农历 2100 年）被**静默值初始化为 0**。
2. 农历 2100 年每月都被当作 29 天（一年 348 天）→ **整年农历全错**。
3. 越过农历 2100 年末后循环推到 `lunarYear = 2101`，读 `lunarInfo[201]`
   —— **数组只有 201 项（下标 0..200），这是越界读，未定义行为**。

实测定位（**农历 2100 年从 2100-01-10 开始**）：

```
2100-01-07 -> 【己未】（羊）年 腊月廿八
2100-01-08 -> 【己未】（羊）年 腊月廿九
2100-01-09 -> 【己未】（羊）年 腊月三十     ← 最后一个算得对的日子
2100-01-10 -> 【庚申】（猴）年 正月初一     ← 进入表项缺失的农历 2100 年
2100-12-28 -> 【辛酉】（鸡）年 正月初五     ← 辛酉是 2101 年，表里根本没有
```

**修法**：
- `std::array<int, 201>` → **`200`**（与数据一致，消除"留一个 0"的陷阱）
- **循环内加范围防御**：一旦 `lunarYear` 超出表范围就抛明确错误，**永不越界读**
- `isValidDate` 上界收紧到 **`2100-01-09`**（`2100-01-09` 是农历 2099 年腊月三十；
  2100-01-10 起进入不可解的农历 2100 年）
- 下界保持 `1901-01-01`（表其实从 1900-01-31 起有效，但用户选择不放开）

> 备选（用户已知，当时未选）：上界取 `2099-12-31`，更"整齐"，但白丢
> 2100-01-01..09 这 9 天 —— 那 9 天其实算得对。

## 5. 缺陷二/三：三个表项与权威值不符

对照权威表：Debian `lunar` 包
[`tables.h`](https://sources.debian.org/data/main/l/lunar/2.2-4/tables.h)
（GPL，Fung F. Lee / Ricky Yeung，覆盖 1900–2049，带官方 2033 修正）。

**1900–2049 区间内共 5 处不一致**（逐项 diff 实测）：

| 年份 | 文件值 | 权威值 | 判定 |
|---|---|---|---|
| 1954 | `0x0a5b0` | `0x0a5d0` | **文件是对的**，不动（见下） |
| 1956 | `0x052b0` | `0x052d0` | **未定**（见下） |
| **1996** | `0x055c0` | `0x05ac0` | **错，修** |
| **2033** | `0x04bd0`（闰月 0） | `0x04afb`（**闰十一月**） | **错，修** |
| **2034** | `0x04ad7`（伪造闰七月） | `0x04ad0`（无闰月） | **错，修** |

### 5.1 2033 / 2034 —— 著名的「2033 年问题」

权威依据：[Debian `lunar` 包 2033 修正补丁](https://sources.debian.org/patches/lunar/2.2-4/05_fix_output_on_year_2033.diff/)
（原文：*"The year 2033 is a special case in modern Chinese Lunar Calendar,
as the 冬至 must be on 11th month"*）。

**注意两个值别搞混**：Debian 的**原始**值是 `0x04bd7`，官方修正为 `0x04afb`；
而**本文件**里 2033 写的是 `0x04bd0`（第三个不同的值，同样错）。
无论哪个错值，**目标都是 `0x04afb`**。

实测症状：

```
2034-02-19 -> 【甲寅】（虎）年 二月初一       ← 应为 正月初一（2034 真春节）
2034-01-21 -> 【甲寅】（虎）年 正月初一       ← 程序把春节报早了整整一个月
```

**2035 年起自动恢复正常**（2033/2034 两年的错误互相抵消）：

```
2035-02-08 -> 【乙卯】（兔）年 正月初一   ✓（真春节 2035-02-08）
2036-01-28 -> 【丙辰】（龙）年 正月初一   ✓
2037-02-15 -> 【丁巳】（蛇）年 正月初一   ✓
2038-02-04 -> 【戊午】（马）年 正月初一   ✓
2039-01-24 -> 【己未】（羊）年 正月初一   ✓
2040-02-12 -> 【庚申】（猴）年 正月初一   ✓
```

→ **错误范围被限定在农历 2033 与 2034 两年内**，不是"2034 以后全错"。

### 5.2 1996 —— 农历差一天

文件 `0x055c0`，权威 `0x05ac0`。

```
1996-09-27 -> 【丙子】（鼠）年 八月十六    ← 错
```

外部依据：1996-09-27 是**农历八月十五（中秋）**——
[wnl.cc](https://www.wnl.cc/1996/0927.html)、[911cha](https://mnongli.911cha.com/1996-9-27.html)
均如此记载。

### 5.3 1954 不是 bug（★ 这条防止误改）

1954 的表值与权威表不同，但用年鉴核对**文件是对的**：

> 1954-09-11 = 农历八月十五（[黄历](https://huangli.13pc.com/laohuangli/web/1954/1954-9-11.html)）

而程序算出的 1954-09-11 正是八月十五。

**教训**：「与另一个表不同」**不等于**「错」。表值差异必须用**行为**（某日的农历结果）
对照真实历书来判定，不能只看十六进制。**1954 保持原样，不许动。**

### 5.4 1956 未定

无可靠对照，**不下结论、不改**。实施时若要处理，须先找到可信历书交叉验证。

2025 中秋外部依据：[黄历](http://viah.cn/HL.asp?Time=2025-10-06) 记
「公历2025年10月6日 … 农历二零二五年八月十五日(乙巳年 乙酉月 戊申日) 中秋节」。
该条顺带再验证了干支日公式：2025-10-06 = 戊申日，+3 天 = 辛亥，

两者对 60 甲子**互相自洽**（`JDN-1 ≡ JDN+9 (mod 10)`），2000-01-01=戊午、
2024-02-10=甲辰 均与已知参考吻合。

## 6. API（已定，已按 `docs/NAMING.md` 校正）

```jc2
import calendar

calendar.lunar(y, m, d) -> Dict {
    year, month, day, isLeapMonth,
    yearStem: "乙", yearBranch: "巳", yearName: "乙巳", zodiac: "蛇",
    monthName: "正月", dayName: "初一",
    text: "【乙巳】（蛇）年 正月初一"          // 原文串，一字不改
}

calendar.ganzhiDay(y, m, d) -> Dict {
    stem: "戊", branch: "戌", name: "戊戌", text: "戊戌日"
}   // 注意："日"字原是 main() 拼的，本方案归入 text

calendar.roman(y, m, d) -> Dict {
    auc: 2778, aucRoman: "MMDCCLXXVIII",
    long:  "ante diem quartum Kalendas Februarias",
    short: "a.d. IV Kal. Feb.",
    anchor: "Kalends", count: 4, isPridie: false, targetMonth: 2,
    text: "A.U.C. MMDCCLXXVIII\n  ante diem quartum Kalendas Februarias\n  (a.d. IV Kal. Feb.)"
}

calendar.convert(y, m, d) -> Dict { lunar: {...}, ganzhi: {...}, roman: {...} }

calendar.isleapyear(y)    -> Bool      // 见下方命名校正
calendar.daysInMonth(y, m) -> Int
```

### 命名校正

`docs/NAMING.md` §二：谓词一律 **`is` + 全小写**（先例 `isFrozen`→`isfrozen`）。
故 `isLeapYear` → **`calendar.isleapyear(y)`**。其余：`lunar` / `roman` / `convert`
单字全小写 ✓，`ganzhiDay` 多字驼峰 ✓，`daysInMonth` 驼峰 ✓。

**全工程 Dict 字段统一 camelCase（2026-09-20 决定并落地）**：`NAMING.md` 约束的是
**内置名**（全局函数 / 模块函数 / 原型方法），**未覆盖 Dict 字段**；用户另行指定
Dict 字段一律 camelCase，并把存量一并改齐：

| 模块 | 旧 | 新 |
|---|---|---|
| `io.stat()` | `is_dir` / `is_file` | `isDir` / `isFile` |
| `regex.getcontext()` | `max_steps` | `maxSteps` |

（`io.stat` 的 `size`、`decimal.getcontext` 的 `prec`、`window` 的 `button`/`key`/
`keycode`/`x`/`y` 本就是单字，无需改。）本模块字段按此规则：

```
isLeapMonth  yearStem  yearBranch  yearName  zodiac  monthName  dayName  text
stem  branch  name  auc  aucRoman  long  short  anchor  count  isPridie  targetMonth
```

**撞车风险已实测排除**：dict 的原型方法只有
`entries hasKey keys merge removeKey values`，且**点号访问优先读键**
（`d['keys'] = 9` 时 `d.keys` 得 `9`，不是方法）。上列字段名与这些方法名无重合，
即使重合也由键胜出。

## 9. 被否掉的选项（**勿再提**）

| 选项 | 否掉的理由 |
|---|---|
| 1:1 照搬格式化字符串 | 字符串不可计算（不能排序/筛选/进表）；用户选 Dict + 保留原文串 |
| 补齐 201 项、猜填 2100 的表值 | 会"凭猜填值"。用户选收紧上界 |
| 输入 2100 年末时直接报"超出表范围"而不收紧范围 | 用户选了收紧有效范围 |
| 放开下界到 1900-01-31 | 用户选保持 1901 |
| 把 1954/1956 一起"修正"成权威表的值 | 1954 已用年鉴证明文件是对的；1956 无可靠对照。表值差异≠错 |
| 模块名用 `datetime` | `datetime` 是时间戳/时区那一套的名字；本模块是历法，`calendar` 更准确 |
| 删掉 `toLatinOrdinal` 的 `n > 20` 死分支 | 不可达是事实，但删它属于顺手改动、与整合动机无关 |
| 把 `Calendar.cpp` 本体放进仓库 | **用户已定：不入库**，那是用户的玩具（§0） |
| Dict 字段用 snake_case | 用户选 camelCase（`isLeapMonth`）；且存量 `io.stat` / `regex.getcontext` 也已一并改成 `isDir`/`isFile`/`maxSteps`，snake_case 参照物已不存在 |
