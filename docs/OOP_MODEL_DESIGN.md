> 相关：`docs/TRAIT_DESIGN.md`、`docs/JIT_DESIGN.md`、`docs/register_vm_design.md`。

## 一、要解决的问题

现在的实现里，同一个"取成员并调用"的动作有**四套互不相同的机制**，走哪一套取决于三个看不见的事实（接收者是什么类型、成员住在哪个袋子、值是不是函数）：

| 写法 | 接收者落在哪 | 由什么决定 |
|---|---|---|
| `a.who()` 实例方法 | 隐藏通道 `selfContext`，不占参数位 | 成员在类链上 |
| `A.who()` 类上取方法 | `selfContext` = **类** | 成员在类链上 |
| `1.0.sin()` UFCS | **第 0 个实参** | 全局函数兜底 |
| `d.f(1.0)` 字典的键 | `selfContext` = 字典 | 名字在字典里 |
| `sys.clock()` 命名空间 | `selfContext` = 命名空间 | 名字在命名空间里 |
| `h.cb()` 实例挂的闭包 | `selfContext` = 实例 | 名字在实例上 |

同时"读成员"有两种结果：`a.who` / `A.who` / `1.0.sin` / `sys.clock` 读出**绑定过的克隆**（每次读都新建一个对象），而 `d.f`（字典的键）/ `h.cb`（挂的闭包）读出**裸值**。

由此产生六个已实测的缺陷：

1. `a.who == a.who` → `false`；`a.who == A.who` → `false`。同一个方法，比不相等。
2. `g = a.who; g()` 能调（保留了读时的接收者），但 `k = h.cb; k()` 报 `'self' accessed outside of context`；两套语义。
3. `1.0.sin` 显示成 `<function sin()>`（参数表被砍掉一位），`d.f` 显示成 `<function sin(x)>`；同一个函数两种签名。
4. 报错文案分叉：`s(0)` → `Function 'sin' expects 0 arguments`，`1.sin(0)` → `Method 'sin' expects 0 arguments`。
5. 参数个数检查分叉：`g = 7.add3; g(3,4)` → `703`（第 2 个实参被静默丢弃），`7.add3(3,4)` → 报错。
6. **`const` 完全不一致**：

| 写法 | 现在 |
|---|---|
| `const cf = 1` 转 `k.cf = 11` | 拒绝 ✓ |
| `const cm() = 2` 转 `k.cm = 12` | **写成功** ✗ |
| `static const scf = 3` 转 `k.scf = 13` | **写成功** ✗ |
| `const cf = 1` 转 `K.cf = 21` | 写成功 ✓（新建 static，本来就该如此） |
| `const cm() = 2` 转 `K.cm = 22` | 拒绝 ✗（实例域的 const 不该管类上的写入） |

即**字段和方法各保护一半，类和实例各保护一半**——该保护的地方没保护，不该拦的地方去拦。

**正确的分界是「域」，不是「成员种类」**：`.名字` 左边是谁，就只碰谁的袋子。
`K.名字 = 值` 只写类袋子（static 域），看不看得见 `const` 只看 **static 域里有没有同名 const**；
`k.名字 = 值` 只写实例袋子，`const` 只看**实例域**里那份。
实例域声明的 `const cf = 1` 与 `K.cf = 21` **毫无关系**——后者应该在 static 域里新建一个 `cf`。

**根因**在 `IRBuilder.cpp:3864-3890`：类体里的**方法**编译成 `IROp::MethodConst` 等，写进**类袋子**；类体里的**字段**（非 lambda）编译成 `<fieldinit>` 内的 `DEFINE_PROP`，写进**实例袋子**（`IRBuilder.cpp:1313`）。两条写入路径各查各的 `is_const`，谁也不看对方。

另外：`static` 在运行时**没有任何标记**。`static` 与实例方法都写进同一个 `cls->properties`，`PropertyDescriptor`（`Value.h:536`）只有 `val / is_const / is_local / is_abstract`，没有 `is_static`。两者目前只能靠"是哪个 opcode 写进去的"隐式区分。

## 二、模型

### 2.1 一条调用规则

> **`a.名字(实参)` = 调用 `名字`，`self = a`，实参就是实参。**

- 名字的解析，**读和调用走同一条顺序**：
  1. `a` 自己的袋子（类实例的袋子里已经装了类体成员，见 §2.4；字典的袋子里是它的键）
  2. **它所依附的原型**（原生容器的 `listProto` / `dictProto` / `stringProto` / `matrixProto`；类实例的模板已在构造时进了袋子，所以这一步对实例是空的）
  3. 全局
- 调用行为**与名字在哪一级找到无关**（自己的袋子、原型、全局，一律 `self = a`）。
- **不做任何隐式参数填充**：接收者只进 `self`，永远不占实参位。
- **代价（已认下）**：字典的键和原型成员同名时**键优先**。所以字典里恰好有个叫 `keys` / `append` 的键时，`D.keys()` 会去调那个键的值（调不动就报 `Target is not callable`），而不是列键。换来的是读和调用只有一条顺序，不再出现"读一套、调一套"。

这是整个模型的核心：**接收者走隐藏通道，不走参数位。**

### 2.1.1 例外：协议方法（dunder）只在类域解析

`__len__` / `__str__` / `__eq__` / `__getitem__` / `__iter__` / `__next__` / `__call__` / `__hash__` 这些
是**语言协议**，不是普通成员，所以它们**不走 §2.1 的顺序**：

- `len(d)`、`str(d)`、`d == o`、`d[i]`、`d[i] = v`、`for x in d`、`x in d`、`d(...)`、`hash(d)`
  一律**沿类链查模板**（本类模板 → `parent` 链），**不看实例袋子里的那份**。
- 因此 `d.__len__ = f` 之后：`d.__len__` 读得到、`d.__len__()` 也调得动（它就是实例袋子里的一份普通值），
  但 **`len(d)` 仍然用类上的模板**——和 Python 一样（隐式查找走类型槽位，不走实例字典）。
- 理由：协议不该被实例上的一次误赋值静默改掉。`obj.__iter__ = something` 这种手滑，代价是整条
  `for` 循环语义变了，而错误现场离赋值处很远。
- 代价（已认下）：同一个名字会出现"读一套、派一套"——`d.__len__` 给影子、`len(d)` 给模板。
  **这条不对齐只限 dunder**，普通成员照旧读调一致。
- 类上写 `D.__len__ = f` 也只新建一个 static（§2.6），既碰不到模板，也碰不到任何实例袋子。

### 2.2 `a.名字` 读出什么

**裸值。** 不复制、不包装、不绑定、不分配。

- `a.who == a.who` 为 `true`；`a.who == A.who` 为 `true`（同一个函数对象）
- `g = a.who; g(x)` 与 `a.who(x)` 不同：前者没有接收者（`g` 里读 `self` 会报 `'self' accessed outside of context`）
- 这不是本模型特有的：JavaScript 里 `const g = a.f; g()` 同样丢 `this`

要给"取出来再调用"补上接收者，用现成的写法（实测都可用）：

```jc2
f = a.add(_)        // 占位符柯里化：当场把接收者和函数一起固定
g = () => a.add(5)  // 闭包：每次调用重新查成员
a |> .add(5)        // 管道成员调用
```

**不提供 `bind` / `call` / `apply`。** 实现 `bind` 必须复制闭包、写 `boundSelf`、打标志、让 `alignArguments` 认这个标志、再偏移 `minArgs/maxArgs/toString` 并分叉报错文案——那就是现有的 `isUFCS`(43 处) + `boundSelf`(79 处) 全套，迁移的主要收益会全部作废。

### 2.3 每个对象一个袋子

| | 袋子里装什么 |
|---|---|
| **实例** | 它自己的全部成员：字段的值 + 方法的闭包（构造时放进去的） |
| **类** | 只有 `static` 成员 |
| 字典 / 命名空间 | 它自己装的东西 |

`X.名字` 一律是"先查 `X` 的袋子，再查全局"。类不过是一个袋子装 static 的对象。

### 2.4 构造与快照

> **类体里的每个成员定义 = 构造时对这个实例求值一次。** 字段和方法同一条规则。

- `items = @[]` → 每实例一个新列表（实测：`a.items`、`b.items` 互不影响）
- `who() = ...` → 每实例一个新的闭包对象
- 因此 `A.who = 新函数` **不影响任何已经造出来的对象**

**实现上按捕获情况分流**：没有捕获（upvalue）的闭包，新建一份和共享一份在可观察行为上完全相同，因此共享一份；**有捕获的（方法体内 `state`、或捕获了类体局部）每实例一份**。这不是语义分情况，是可观察等价的优化。

- 附带写明：*函数对象的身份不保证每实例不同*
- 今天全部测试/示例/模块里，类体方法用 `state` 的次数是 **0**，所以实际上几乎不付钱

**快照的代价**（实测，20 万个对象、10 个成员）：

| | 每对象 | 相对基线 |
|---|---|---|
| 只构造 | 1.02 µs | 1× |
| + 抄 10 个指针（共享） | 3.37 µs | 3.3× |
| + 每实例新建 10 个无捕获闭包 | 13.8 µs | 13.6× |
| + 每实例新建 10 个带捕获闭包 | 21.7 µs | 21× |

单个闭包新建 0.75 µs（无捕获）/ 1.54 µs（带捕获）；纯 `map` 插入 0.24 µs/成员。

**顺序要求**：**必须先做"成员编号 + 实例扁平槽位"，再做快照。** 否则光是拷贝就让对象构造慢 3 倍。

### 2.5 `self`

- **所有函数**都能读 `self`；它由调用形式填充：`a.f(x)` → `self = a`，普通调用 `f(x)` → `self` 为空（读它报 `'self' accessed outside of context`）
- 因此 `f` **不需要是 `a` 的成员**：
  ```jc2
  f() = "self 是 " + str(self)
  A = 1
  A.f()        // self = 1
  ```
- `self` 是**保留名**（全局保留），且**不是变量**：`self = 5` → `SyntaxError: 'self' is a reserved keyword...`，`self += 1` → `SyntaxError: Unsupported compound assignment target`。它只能做 `self.成员`

### 2.6 赋值

| 写法 | 行为 |
|---|---|
| `a.名字 = 值`（实例） | 写实例袋子：已存在就覆盖（`const` 就拒），不存在就**挂一个新字段** |
| `C.名字 = 值`（类） | **命中就覆盖（`const` 就拒），没命中就新建一个 `static`。** 不看这个名字装的是方法模板、字段声明还是 static。前提是 `C` 不是 `is_frozen` |

**一条规则，不看成员种类。** 一个名字在类袋子里只有一格，所以"新建同名 static"只会发生在
名字缺席时；名字存在时是**覆盖那一格**——若覆盖的是方法模板，**已经造出来的对象不受影响**
（第 9 步的快照），新对象用新模板。

**`const` 按域生效，不按成员种类。** 类写入只在 **static 域**里看 `const`：

| 声明 | 写 `K.名字`（类 / static 域） | 写 `k.名字`（实例域） |
|---|---|---|
| `const cf = 1`（实例字段） | **新建 static** | 拒绝 |
| `const cm() = 2`（实例方法） | **新建 static** | 拒绝 |
| `static const scf = 3` | 拒绝 | 实例上找不到 |
| `static const scm() = 4` | 拒绝 | 实例上找不到 |
| `nf = 4` / `nm() = 5` | 新建 static | 覆盖 |

这条要求 static 域与实例成员模板**分属两张表**：否则"在 static 域里新建一个 `who`"
会顶掉同名的实例方法模板。物理拆分属于"统一写规则"那一步（见 §六 进度表）。

### 2.7 `static`

只住类袋子，**实例查找不经过它**。因此 `a.tag` 找不到、`a.tag()` 报找不到。

### 2.8 类、trait 与 `is_frozen`

**两级冻结，不要混为一谈：**

| 级别 | 什么时候 | 冻住什么 |
|---|---|---|
| **模板冻结** | 类定义完成时 | 只冻**实例成员的模板**——运行期没有任何手段能改它。**类本身不是 `is_frozen`**，static 域照旧可写（这正是 §2.6"新建 static"的来源） |
| **`is_frozen`** | trait 定义完成时自动；或显式 `freeze()` | 冻住**整个类**——模板和 **static 域都冻**，加/改/删一律报错 |

`is_frozen` 必须覆盖 static 域，因为 **`is_frozen` 是"可哈希"的前提**：实测未冻结的实例放进字典键报 `unhashable type`，`freeze()` 之后才可用。而冻结实例的哈希**按内容算**（类名 + 全部成员），所以只要还有一个能改的口子，用它做键就不成立。

实测的现有行为（**保留，不要改**）：

```jc2
trait T { m() = 1 }
T.s2 = 1     ->  RuntimeError: Cannot modify frozen trait 'T'.   // static 域也冻住了
T.m  = ...   ->  RuntimeError: Cannot modify frozen trait 'T'.
```

**`is_frozen` 一旦为真，`C.名字 = 值` 的"新建 static"路径不再可用。**

其余：

- **改类的唯一途径是重写类体**，那会产生一个**新的类对象**；老对象指着老类对象，于是 `isinstance(a, A)` 变 `false`——它们成了没有名字的类型的实例
- 配套纪律：**改完类就重新造对象**。语言只保证"不改老对象"，不保证你手里没留着老对象

### 2.9 `super` 与 `classContext`

**`classContext` 统一改成词法来源：当前正在执行的那个闭包的 `owner_class`**（`Value.h:1725`，已在 `VM.cpp:6623` 设置，序列化也带）。

今天它有两个来源：实例查找时顺手得到的 `owningClass`（`VM.cpp:2368/2388`）和闭包的 `boundClass`。**快照之后实例查找不走类链，`owningClass` 那条来源不存在了**，所以只能改成词法来源。这一条同时收掉三个用途：

| 用途 | 位置 |
|---|---|
| `super` | `execSuperInvoke`（`VM.cpp:2454`） |
| `class` 关键字 | `VM.cpp:4468` |
| 私有成员解析的候选 | `collectPrivateCandidates`（`VM.cpp:340-351`），其中 `lexical` 本来就是 `closure->owner_class` |

顺带能删掉 `execInvoke` / `execCall` 里整条 `owningClass` 传递链。

- **`super.f(x)` 是模型里唯一的特殊形式**：`super` 不是对象表达式，套不进 §2.1 的规则，所以它的接收者 = **当前 `self`**
- **static 方法里 `super` 报错**（今天也报错）
- **trait 方法里 `super` 报错**：trait 的 `parent` 是 `nullptr`。要"先跑父类实现再叠加"，就在宿主类里重写那个方法。全部测试/示例里没有一处在 trait 方法内用 `super`（`super.` 只出现在 4 个游戏的 `super.init()` 和 3 个类继承测试里），零迁移成本

### 2.10 与 Python / JavaScript 的关系

| | 接收者怎么来 | 读 `a.f` | 方法存放 | 改类对老对象 |
|---|---|---|---|---|
| Python | 读时绑（`__get__`） | 新建 method 对象 | 类上，动态查 | 生效 |
| JavaScript | 调用形式决定，进 `this` | 同一个函数对象 | 原型上，动态查 | 生效 |
| **本模型** | 调用形式决定，进 `self` | 同一个函数对象 | **抄进实例（指针副本）** | **无效** |

即**取 JS 的零判据 + 比 JS 更彻底的实例模型**（JS 的方法在原型上共享，所以 JS 的对象并不真正拥有自己的方法）。不采用 Python 的读时绑定（它需要判据）；不采用"接收者当第 0 个实参"（它会让 `d.f(1.0)` 变成 `sin(字典, 1.0)`，并且和"零判据"直接冲突）。

### 2.11 快照的适用范围：只对类实例，原生容器走共享原型

**快照只适用于有"构造脚本"的对象，也就是类实例（`ObjInstance`）。** 原生容器（list / dict / set / string / matrix）的成员住在**共享原型**（`listProto` / `dictProto` / `stringProto` / `matrixProto`）上，查找**永远是动态的**。所以 `.append()` / `.keys()` / `.upper()` / `.floor()` 全部照旧。

为什么必须这样：

1. 容器**没有构造脚本**——它们是 C++ 侧 `allocate<ObjList>()` 出来的，没有一个"构造时刻"可以拿来做快照
2. 容器是分配最频繁的类型；每次造一个列表就拷一份原型成员（十几个）完全不现实
3. 快照要靠"成员编号 + 扁平槽位 + 溢出表"三件套，而 `ObjList` / `ObjDict` / `ObjSet` **根本没有 `properties` 成员表**（`Value.h:995/1008/1053`），只有 `vec` / `elements` / `cached_hash`

**这不是可观察的分情况。** 调用行为仍然是同一条规则（`self` = 接收者、实参就是实参、读出来是裸值）；区别只在"查找走到哪一级"，而原型是内置单例、脚本里够不到（`list` 是个函数，不是那个原型对象），所以"改原型会影响已有列表"这件事观察不到。

实测到的三件事，都写进对比表：

- **容器不能挂字段**：`L.x = 1` / `S.x = 1` → `Cannot set property on this type.`。但 **`D.x = 1` 可以**——字典的"成员"就是它的键。所以"实例可以挂字段"只对**类实例**成立；字典挂的是键。
- `L1.append == L2.append` 今天是 `false`（读时克隆）；新模型下是 **`true`**（原型上同一个函数，读出来是裸值）。
- **读和调用的查找顺序今天不一致**：`D.keys = f` 之后，`D.keys`（读）给的是那个**键的值**，而 `D.keys()`（调）走的却是**原型方法**（返回键列表）。§2.1 的统一顺序把它改成"读和调用一致，自己的袋子优先"——**已定：键优先、读调一致**。代价记在 §2.1。

| 3 | `a.who == A.who` | `false` | `true` | **变** |
| 4 | `a.who()` | `A:7`（self=a） | `A:7` | 不变 |

## 四、为什么不选另外几条路

| 路 | 为什么不行 |
|---|---|
| 接收者当**第 0 个实参** | 调用点必须知道"这一位是不是接收者"→ 必须有判据（"在哪找到的"或"类体声明过没有"）。而且会让 `d.f(1.0)` 变成 `sin(字典, 1.0)` |
| **读时绑定**（Python） | 同样需要判据："在 type 上找到才绑"。而且要每读一次分配一个包装对象 |
| **UFCS 的隐式参数填充** | 与"接收者只走一个通道"直接冲突：`A.f()` 里 A 既进 `self` 又占参数位，0 参自由函数永远不可用 |
| 允许 `C.名字 = 值` **覆盖方法模板** | 覆盖进去的是一个**值**，而构造时要做"每实例一份"，语义没有定义：从外面塞进来的闭包，它的捕获**已经初始化过了**，克隆时是重置还是共享？没有干净答案 |
| 提供 **`setDefault`** 之类改模板的 API | ① 字段默认值是**代码**不是值，传值只覆盖常量；② 传值会破坏"实例之间零共享"（所有新实例拿到同一个列表）；③ 传工厂就等于覆盖模板，回到上一条；④ 它会让"源码写着 `items = @[]`、新对象拿到 `@[9]`"——一个看不见的第二来源 |

**整条路的转折点是那一个岔路口**：接收者放**参数位**还是放**隐藏通道**。

- 放参数位 → 必须知道"这一位是不是接收者" → 必须有判据 → 判据要么看不见（在哪找到的），要么是个隐藏位
- 放隐藏通道 → 不需要判据 → 但接收者得有个名字 → `self` 必须是保留名

没有第三条路。

## 七、实施时要核的点

1. **`1.0.floor` 的归属**：`1.0.floor(1,2)` 报的是 `Function 'floor' expects 1 or 2 arguments, got 3`（走全局），但 `1.0.floor` 读出的是 `<function floor(n)>`（不像 UFCS 的裁剪显示）。数字那几个原生成员/全局函数要逐个核一遍，确定砍 UFCS 后哪些会失效。
2. **`L.sum(5)` / `S.upper(5)` 静默吞掉多余实参**：`VM.cpp:2420` 的检查是 `if (maxArgs() > 0 && restName.empty())`——`maxArgs()==0` 时**整个检查被跳过**。这是既有缺陷，顺手修。
3. **`a.f(_)` 占位符柯里化**：目前是编译器机制，与成员查找的交互（固定的是当时查到的那个函数）要在第 2 步之后回归确认。实测：`f = a.add(_)` 建好之后把 `A.add` 换成 `(y) => 999`，`f(5)` 仍是 `15`（当场固定）。
4. **trait 成员的 `is_static` 传递**：trait 复制路径（`TRAIT_DESIGN.md` §七.2）要跟着带。
5. **`freeze()` / `isFrozen()` 缺 CLASS 分支**：实测 `freeze(A)` 返回"成功"但什么都没做，`isFrozen(A)` 永远为 `false`——连内部 `is_frozen = true` 的 trait 也报 `false`。既然 `is_frozen` 是"可哈希"的前提，这个缺口要补：`freeze(C)` 真的把类置冻结，`isFrozen(C)` 如实返回。同时确认 `CONST` 与 `is_frozen` 的关系（`const` 是成员级的，`is_frozen` 是整体的）。
