# JC2 寄存器虚拟机 (Register VM) 架构设计白皮书

本文档详细记录了 JC2 引擎从基于栈的虚拟机（Stack-based VM）重构为基于寄存器的虚拟机（Register-based VM）的核心架构设计。

---

## 1. 指令集架构 (ISA) 设计

采用经典的 **32-bit 定长指令集**，以最大化虚拟机的解码（Decode）和分发（Dispatch）效率。所有指令均被打包为一个 `uint32_t`，VM 在执行时只需一次内存读取即可获取操作码和所有操作数。

### 1.1 指令格式
指令分为四种基础格式：
*   **格式 A (iABC)**: `[OpCode: 8位] [A: 8位] [B: 8位] [C: 8位]`
    *   用于算术运算、逻辑运算、比较等。例如 `ADD A B C` (`Reg[A] = Reg[B] + Reg[C]`)。
*   **格式 B (iABx)**: `[OpCode: 8位] [A: 8位] [Bx: 16位无符号]`
    *   用于加载大常量、全局变量访问、闭包创建等。
*   **格式 C (iAsBx)**: `[OpCode: 8位] [A: 8位] [sBx: 16位有符号]`
    *   用于条件跳转、循环等控制流。`sBx` 采用 `+ 0x7FFF` 偏置编码（支持 ±32,767 条指令跳转）。
*   **格式 D (iAx)**: `[OpCode: 8位] [Ax: 24位无符号]`
    *   用于 `EXTRAARG` 扩展指令，提供 24-bit 的超大操作数。
*   **格式 E (isAx)**: `[OpCode: 8位] [sAx: 24位有符号]`
    *   用于无条件超远距离跳转 (`JMP`)。`sAx` 采用 `+ 0x7FFFFF` 偏置编码（支持 ±8,388,607 条指令跳转）。

### 1.2 治愈“火力不足恐惧症”：EXTRAARG 扩展与蹦床机制
为了彻底打破 8-bit 和 16-bit 操作数的物理限制，我们引入了极其优雅的扩展机制，使得寄存器机能够轻松支持千万级别的常量、闭包和元数据索引：

**1. EXTRAARG 扩展后缀 (The Suffix Extension)**
为了打破 8-bit 和 16-bit 的物理限制，我们引入了 `EXTRAARG` 扩展指令。当操作数达到特定的“转义标志”时，VM 会自动读取紧随其后的 `EXTRAARG Ax` 指令，将其 24-bit 的 `Ax` 作为真实操作数。
*   **双轨转义防冲突**：由于 K-Bit 占用了最高位，`0xFF` 会被误认为常量 127。因此我们精细化了转义标志：
    *   不带 K-Bit 的操作数（如 A）和 16-bit 操作数（Bx）：转义标志为 `0xFF` 和 `0xFFFF`。
    *   带 K-Bit 的操作数（如 B, C）：寄存器转义标志为 `0x7F` (127)，常量转义标志为 `0xFF` (255)。
*   **多重扩展序列**：如果一条指令有多个操作数触发了转义（如 `BUILD_LIST 255, 255, 255`），VM 会按 A -> B -> C 的顺序，依次读取紧随其后的 3 条 `EXTRAARG` 指令。这保证了极简且无歧义的解码逻辑。
*   **统一寄存器/溢出槽寻址 (Unified Address Space)**：这是本架构最惊艳的设计！当寄存器索引被 `EXTRAARG` 扩展到 `>= 128` 时，VM 会自动将其解析为**溢出槽索引**（`SpillSlot[Ax - 128]`）。
    *   这意味着物理寄存器（0~126）和溢出槽（128~16777215）在指令集层面被统一成了一个高达 1677 万容量的连续地址空间！
    *   对于需要大量连续寄存器的变长指令（如 `CALL`, `BUILD_LIST`, `BUILD_MATRIX`），如果参数超过 128 个，寄存器分配器会自然地将它们分配到连续的溢出槽中。指令只需通过 `EXTRAARG` 将起始寄存器指向溢出槽，即可完美实现**无限参数传递**和**无限大容器构建**，彻底消灭了操作数溢出恐惧！

**2. 蹦床机制 (Trampoline)**
在 32-bit 定长指令中，条件跳转（如 `JMP_TRUE A, sBx`）需要占用 8 位寄存器 A，因此偏移量 `sBx` 只能分配 16 位（±32,767 条指令，约 128KB 机器码）。
为了优雅地支持**无限大**的函数体，编译器在遇到超过 16 位限制的条件跳转时，会自动发射**蹦床 (Trampoline)**：
*   **条件跳转超限**：`JMP_TRUE A, far_target` 自动降级为：
    1. `JMP_FALSE A, +1` (如果不满足，跳过下一条指令)
    2. `JMP far_target` (使用 24-bit 的 `isAx` 格式，支持跨越 33.5MB 机器码)
*   **异常捕获超限**：`TRY_BEGIN A, far_catch` 自动降级为：
    1. `TRY_BEGIN A, +2` (将 catch 块设为下下条指令)
    2. `JMP normal_continue` (正常执行时跳过蹦床)
    3. `JMP far_catch` (蹦床：发生异常时落入此处，弹射到真实的 catch 块)
*   **迭代器超限**：`ITER_NEXT A, far_end` 自动降级为：
    1. `ITER_NEXT A, +1` (如果耗尽，落入下一条指令的蹦床；如果成功，PC+=2 自动跳过蹦床)
    2. `JMP far_end` (蹦床：弹射到循环结束处)

通过这种极其优雅的编译器降级策略，VM 的指令集保持了绝对的精简和正交，同时获得了近乎无限的控制流跨度！

### 1.3 K-Bit 常量复用机制
在 `iABC` 格式中，B 和 C 操作数只有 8 位。为了减少频繁的 `LOADK` 指令，我们引入了 **K-Bit 机制**：
*   B 和 C 的最高位（第 8 位，即 `0x80`）若为 `1`，则表示该操作数是**常量池索引**（0~127）。
*   若为 `0`，则表示**物理寄存器索引**（0~127）。
*   **超量常量回退 (Constant Fallback)**：如果常量池索引 >= 128，编译器会先发射一条 `LOADK` 指令（配合 `EXTRAARG` 扩展），将该常量加载到保留的暂存器中，随后在主指令中将其作为普通寄存器操作数使用。

### 1.3 核心指令集概览
*   **数据搬运**: `MOVE`, `LOADK`, `LOADKX`, `LOAD_NIL`, `LOAD_BOOL`
*   **算术逻辑**: `ADD`, `SUB`, `MUL`, `DIV`, `MOD`, `POW`, `BAND`, `BOR`, `BXOR`, `SHL`, `SHR` (均支持 K-Bit)
*   **控制流**: `JMP`, `JMP_TRUE`, `JMP_FALSE`, `EQ`, `NEQ`, `LT`, `LE`, `GT`, `GE`
*   **函数与 OOP**: `CALL`, `TAIL_CALL`, `INVOKE`, `SUPER_INVOKE`, `GET_PROP`, `SET_PROP`, `CLASS`, `METHOD`
*   **容器与模式匹配**: `BUILD_LIST`, `BUILD_DICT`, `INDEX_GET`, `SLICE_GET`, `MATCH_TYPE`, `MATCH_SHAPE`

## 2. 编译器中端与 IR 设计 (Sea of Nodes)

为了支持高级的寄存器分配和优化，编译器引入了基于 **Sea of Nodes** 架构的中间表示（IR）。

### 2.1 图结构与依赖分离
放弃了传统的线性基本块（Basic Blocks）和三地址码（TAC）。在 IR 图中，节点之间的依赖被显式分离为两类：
*   **控制依赖 (Control Input)**：决定节点的执行顺序和副作用的发生时机（如 `If`, `Merge`, `Call`）。
*   **数据依赖 (Data Inputs)**：决定节点计算所需的数据来源（如 `Add` 依赖两个操作数）。

### 2.2 静态单赋值 (SSA) 与 Phi 节点
*   所有局部变量在 IR 构建阶段被转化为 SSA 形式，每次赋值都会产生新的虚拟寄存器。
*   在控制流汇合点（如 `If` 结束后的 `Merge` 节点，或 `While` 循环的 `Loop` 节点），自动插入 **Phi (Φ) 节点**，根据实际执行的控制流分支选择对应的数据版本。

### 2.3 IR 优化管线 (IROptimizer)
在生成字节码前，IR 图会经过多趟（Multi-pass）工业级优化：
1.  **常量折叠 (Constant Folding)**：安全地在编译期计算两端均为常量的纯运算。
2.  **控制流折叠 (Control Flow Folding)**：当 `If` 条件为常量时，直接重定向控制流，切断死分支。
3.  **常量去重 (Constant Deduplication)**：合并图中值相同的 `Constant` 节点，极大地压缩常量池。
4.  **Phi 节点简化 (Phi Simplification)**：消除所有输入来源相同的冗余 Phi 节点。
5.  **死代码消除 (Dead Code Elimination)**：通过正向可达性分析和逆向标记-清除（Mark-and-Sweep），回收所有无副作用的孤立计算节点。

## 3. 寄存器分配器 (Register Allocator)

将无限的虚拟寄存器映射到有限的物理寄存器上。

### 3.1 物理寄存器与溢出槽
*   **物理寄存器 (0~127)**：受限于 K-Bit 机制，物理寄存器上限为 128 个。
*   **暂存器保留**：硬性保留 3 个物理寄存器（R125, R126, R127）作为暂存器，用于超量常量回退和极端溢出恢复。
*   **溢出槽 (>=128)**：当物理寄存器耗尽时，变量会被分配到溢出槽中。

### 3.2 Chaitin 图着色算法
1.  **指令调度**：将 Sea of Nodes 展平为带有基本块的 CFG，并进行局部拓扑排序。
2.  **Phi 去结构化**：在 `Merge` 和 `Loop` 的前驱块末尾插入 `Move` 指令，销毁 Phi 节点。
3.  **活跃变量分析**：计算每个基本块的 `LiveIn` 和 `LiveOut` 集合。
4.  **冲突图构建**：为生命周期重叠的虚拟寄存器连边。
5.  **Move 偏好 (Coalescing)**：在着色时，优先尝试为 `Move` 指令的源和目标分配相同的颜色，从而在最终字节码中消除冗余的搬运指令。
6.  **启发式溢出**：当图不可着色（K=125）时，挑选度数最大的节点作为牺牲者，分配至溢出槽。

## 4. 函数调用约定 (Calling Convention)

采用**零拷贝传参**的连续寄存器窗口（Register Window）调用约定。

*   **纯粹的寄存器内存模型**：彻底抛弃传统的 Push/Pop 栈。VM 维护一个全局的连续寄存器数组 `Value registers[]`。每个函数调用时，分配一个固定大小的寄存器窗口（例如 256 个槽位，前 128 个为物理寄存器，后 128 个为溢出槽）。
*   **常规调用**：调用方将参数放置在自己窗口末尾的连续寄存器中。执行 `CALL` 时，新帧的 `registerBase` 直接滑动并指向第一个参数所在的寄存器，实现零拷贝传参。
*   **超大参数调用**：得益于 Unified Address Space 设计，当参数数量过多无法放入物理寄存器时，编译器将参数连续分配在**溢出槽**中。`CALL` 指令通过 `EXTRAARG` 将起始寄存器指向溢出槽。VM 执行时，将新帧的 `registerBase` 指向溢出槽的起始位置，对新函数而言，这些溢出槽天然成为了它的 `R(0)`、`R(1)`，完美实现跨越物理限制的零拷贝。
